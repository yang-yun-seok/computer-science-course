## 1. 공통 작성 규칙

- 아래 A/B 조건은 제작할 학습 시나리오다. 현재 UI에 없는 설정은 “보완 필요”로 명시하고 어댑터 또는 작은 모델 변경으로 연결한다.
- 각 미션은 한 가지 비교축만 변경한다. 관찰 시점을 비교하는 미션은 같은 실행의 전후라는 점을 명시한다.
- 입력·알고리즘·정책이 같은데 결과도 같은 비교 역시 가능하다. 왜 결과가 유지되는지 설명하게 한다.
- 측정 숫자는 참조 설계값이다. 배포 전 기존 테스트·독립 계산·실제 브라우저 결과로 다시 대조한다.
- 표에 적은 “예상 결과”는 제작자용이다. 학생에게는 예측과 실험을 마친 뒤 해설로 공개한다.
- 짧은 미션 하나의 목표 시간은 약 5~8분으로 설계하되 실제 학생 소요 시간으로 검증된 값처럼 표시하지 않는다.
- 기존 도해를 재사용하고 A/B 관측표를 추가한다. 모든 미션마다 새로운 이미지 3장을 별도로 만드는 작업은 포함하지 않는다.
- 이 목록에는 원래 4번 모바일·키보드 전 과정 점검을 추가하지 않는다.

## 3. 대표 미션 6개 상세

### 3.1 M01 — 계산됐는데 왜 아직 화면에 없을까요?

- 위치: CH01-L01 b02, cpu-add.
- 목표: 계산·RAM 기록·화면 출력의 단계 차이를 설명한다.
- 고정 조건: 첫 수 3, 둘째 수 2. 비교축은 관찰 시점.
- 예측: 계산 장치에서 5가 나온 직후 RAM과 화면에도 5가 있을지 적는다.
- A: 같은 초기 조건에서 계산이 끝난 상태까지만 한 단계씩 진행하고 기록한다.
- B: A 뒤 RAM 기록 단계까지 진행하고 기록한다.
- 관측표: 레지스터 결과, RAM 결과, 화면 결과. 숫자 0·아직 없음·5를 구별한다.
- 마지막 조작: 화면 출력 단계까지 진행한다.
- 자기 점검: 계산 결과의 위치 / 메모리 기록 / 화면 출력의 순서를 설명했다.
- 판정: 각 기록 시점이 실제 해당 단계인지 모델 상태로 확인한다.
- 보완 여부: 현재 step 모델을 재사용하며 checkpoint 판정만 연결한다.

### 3.2 M24 — 같은 숫자도 입력 순서에 따라 탐색이 달라질까요?

- 위치: CH08-L01 b03, bst-traversal.
- 목표: 키 개수가 같아도 트리 모양에 따라 탐색 경로가 달라짐을 설명한다.
- 고정 조건: 중복 없는 키 1·2·3·4·5, 찾을 값 5.
- 예측: 두 트리에서 찾기까지 비교할 노드 수를 예상한다.
- A: 처음 넣을 키를 3,2,4,1,5로 설정 → 트리 만들기 → 5 탐색 → 결과 기록.
- B: 처음 넣을 키를 1,2,3,4,5로 설정 → 트리 만들기 → 5 탐색 → 결과 기록.
- 기대값: A 경로 3→4→5·비교3회, B 경로 1→2→3→4→5·비교5회.
- 기록: 실제 searchPath의 노드 수·방문 경로. 없는 높이 지표를 이미 표시하는 것처럼 안내하지 않는다.
- 자기 점검: 동일한 키 집합 / 다른 입력 순서·모양 / 비교 경로의 길이를 설명했다.
- 한계: 모든 입력에서 A가 최적이라는 결론이나 일반 BST의 균형 보장을 주장하지 않는다.
- 보완 여부: 현재 action 재사용. 트리 생성 뒤 실제 탐색이 실행됐는지 판정한다.

### 3.3 M25 — 간선이 적은 길과 비용이 적은 길은 같을까요?

- 위치: CH08-L02 b04, graph-paths.
- 고정 조건: AB=1, BC=1, AC=5, 시작 A, 도착 C.
- 비교축: 탐색 알고리즘.
- A: BFS 실행. 경로 A→C, 간선1개, 실제 가중치 합5.
- B: 다익스트라 실행. 경로 A→B→C, 간선2개, 가중치 합2.
- 현재 모델의 cost는 BFS에서 간선 수, 다익스트라에서 가중치 합을 뜻한다.
- 어댑터는 두 경로 모두 edgeCount와 weightSum을 별도로 계산해 같은 단위끼리 비교한다.
- 원본 그래프의 비용은 변경하지 않는다.
- 자기 점검: 알고리즘의 목표 / 간선 수와 가중치 합 / BFS 최소 비용의 조건을 설명했다.
- 보완 여부: 모델 재작성 없이 경로에서 보조 관측값 추출.
- 경계 확인: 목표 D의 도달 불가를 비용0으로 저장하지 않는다.

### 3.4 M39 — C가 왔는데 ACK가 왜 그대로일까요?

- 위치: CH15-L02 b03, tcp-recovery.
- 고정 조건: A·B·C 각1바이트, 수신 윈도3, 연결 설정 완료.
- 준비: A 전송 → B 유실 → C 도착.
- 예측: B가 없을 때 ACK와 앱에 전달된 내용을 적는다.
- A 기록: ACK2, 앱 A, C는 순서 대기.
- 변경 조작: B 재전송.
- B 기록: ACK4, 앱 ABC, 재전송1회.
- 자기 점검: 누락된 B / 보관된 C / 연속 구간 확장과 누적 ACK를 설명했다.
- 완료 조건: 앱 ABC·ACK4 등 실제 구조화 상태를 확인한다. done이 없다는 이유로 계속 미완료 처리하지 않는다.
- 보완 여부: 기존 action 재사용, 준비 상태·결과 기록의 전제 판정 추가.
- 조건 주의: “유실 복구 끝까지”가 초기 상태를 새로 만드는 동작임을 고려해 A 기록을 보존한다.

### 3.5 M35 — 결과가 같아도 찾는 방법은 달라질까요?

- 위치: CH13-L02 b03, query-plan.
- 고정 조건: 같은 초기 DB·같은 제목 조건·같은 SELECT.
- A: 인덱스 없는 SQL의 실행 계획과 실제 SELECT 결과를 기록한다.
- B: 동일한 초기 데이터에 제목 인덱스를 만든 뒤 같은 질의를 실행하고 기록한다.
- 예상: 준비한 SQLite 버전·데이터에서 SCAN과 SEARCH/USING INDEX 변화. 실제 출력으로 확정한다.
- 지표: 계획 detail, 사용한 인덱스, 결과 행의 내용·개수.
- ORDER BY 없는 결과는 행의 순서 대신 중복 수를 포함한 내용 동등성으로 비교한다.
- 미포함 지표: 실제로 측정하지 않은 시간·예상 행 수·페이지 읽기 횟수.
- 자기 점검: 같은 질문 / 달라진 접근 방법 / 실제 성능은 별도 측정이 필요함.
- 보완 필요: 현재 기본 예시는 EQP 결과만 보여주므로 같은 SELECT의 결과도 함께 수집하는 준비 SQL을 추가한다.
- 비동기 확인: Worker 오류·이탈·초기화·재실행에서 이전 결과가 새 결과로 기록되지 않는다.
- 초기화 확인: 실행마다 DB가 새로 준비되는 현재 SQL 도우미의 실제 동작을 확인하고 이를 A/B 조건으로 고정한다.

### 3.6 M40 — 타이머를 먼저 예약하면 먼저 실행될까요?

- 위치: CH16-L01 b04, event-loop-order.
- 고정 조건: A는 동기 출력, B는 이미 이행된 Promise의 반응, C는 0ms 타이머.
- 비교축: B와 C를 예약하는 코드의 순서.
- A 코드: A 출력 → Promise B 예약 → timer C 예약.
- B 코드: A 출력 → timer C 예약 → Promise B 예약.
- 예상: 두 경우 모두 A→B→C.
- 자기 점검: 현재 태스크 / 마이크로태스크 체크포인트 / 다음 타이머 태스크를 설명했다.
- **보완 필요**: 현재 runActual은 준비 코드 한 종류뿐이다. 허용된 준비 코드 두 종류를 명시적으로 추가한다.
- 학생의 예측 선택만 바꿔 놓고 실제 실행 조건도 바뀌었다고 표시하지 않는다.
- 임의 JavaScript 입력이나 eval은 추가하지 않는다.
- intro·코드 표시·실제 예약 순서를 일치시킨다. 현재 intro와 코드의 예약 순서도 A에서 대조한다.
- 실제 완료까지 기다린 뒤 기록하고 정확한 ms 소요 시간을 정답으로 요구하지 않는다.

## 4. 추가 어댑터 주의사항

| 실습 | 구현 시 확인할 사항 |
| --- | --- |
| memory-save | 학생의 기존 수정 글과 A/B 준비 글을 구별하고 조건 적용 시 초기 상태를 명확히 표시 |
| library-query | 원본 배열이 클로저 안에 있으므로 결과 개수는 모델의 순수 관측 함수로 제공; HTML 파싱으로 계산하지 않기 |
| sql-first·sql-analytics·query-plan | SQL 파라미터·스키마·인덱스가 A/B 사이에 남는지 확인; 실제 Worker 완료 결과만 기록 |
| virtual-memory·graph-paths | Infinity·도달 불가·주소 변환 실패를 숫자0 또는 미실행으로 혼동하지 않기 |
| storage-lifetime | 미션 초안 저장 키와 교육용 저장 실험 키 분리; 비교 준비 과정에서 기존 시험·복습·다른 탭 값을 지우지 않기 |
| crypto-compare | hash·compare도 비동기 동작; run 버튼 이름에만 의존하는 busy 판정을 확대하고 결과 역전 방지 |
| event-loop-order | 새 준비 코드 두 종류 외에는 실행하지 않으며 예약 순서와 실제 실행 순서를 별도로 기록 |
| bounded-queue | 같은 시각 단위의 도착→수락→처리 순서 명시; 백프레셔의 상류 지연은 이 모형의 집계라는 한계 표시 |
| canary-deployment | 비율 변경 전후 같은 요청 수에서 비교; 누적 표본이 섞이지 않게 초기화 |
| observability-recovery | 표본 개수·백분위수 계산 규칙·목표와 실제 시간을 분리해 기록 |

이 목록의 보완은 비교 미션을 실제로 수행하는 데 필요한 범위로 제한한다. 다른 실습 기능이나 교사용 관리 화면을 함께 확장하지 않는다.

## 5. 미션별 제작 완료 체크리스트

각 M번호 작업 시 다음 체크를 복사해서 기록한다.

- [ ] 현재 실습의 실제 입력 이름·버튼·출력 지표에 연결했다.
- [ ] 시작 조건과 바꿀 비교축을 명시했다.
- [ ] 예측 전에 새 실험의 답을 그대로 노출하지 않는다.
- [ ] A/B 모두 유효한 조건에서 실행해 결과를 기록할 수 있다.
- [ ] 기대값을 독립 계산 또는 기존 검증과 실제 실행으로 대조했다.
- [ ] 설정 변경·오류·초기화 후 오래된 결과를 새 결과로 쓰지 않는다.
- [ ] 비동기 작업이면 완료·취소·재실행의 순서를 확인했다.
- [ ] 자기 점검 기준과 모범 설명이 결과의 원인을 설명한다.
- [ ] 미측정 수치나 실제 시스템의 보장을 만들어내지 않는다.
- [ ] 본문·미션·종합 사례에서 같은 개념을 같은 용어로 사용한다.
- [ ] 관련 검수대장 C 완료 수를 한 번만 올렸다.
