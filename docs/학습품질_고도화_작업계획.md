### 1.1 이번 계획에서 제외하는 일

- 원래 4번에 해당하는 모바일·키보드·화면 확대·스크린 리더의 전 과정 점검 프로젝트.
- 학습 진도판, 수준 진단, 맞춤 추천, 교사용 성적 수집, 계정·기기 간 동기화.
- 시험 문항 수 확대, 커리큘럼 대단원 추가, 전체 디자인 교체.
- 용어 1,133개의 재전수 교정. 다만 이번 교정에서 발견한 본문과 연결 용어의 모순은 함께 수정한다.
- 교안과 무관한 저장소 정리, 프레임워크 전환, 전체 시뮬레이터 재작성.

새 미션·사례에서 필요한 버튼·링크·화면 출력의 정상 동작 확인은 각 기능의 완료 기준에 포함한다. 제외한 4번을 별도 검수 단계로 다시 추가하지 않는다. 기존 키보드 조작·반응형·모션 감소 처리는 유지한다.

### 1.2 유지할 제작 기준

- 사이트 제목은 Computer Science, 과정 이름은 1강·2강·3강·부록을 유지한다.
- 초심자에게 용어를 먼저 정의하고, 비유의 대응 관계와 적용 한계를 설명한다.
- 한국어 어절과 문장 흐름을 지키고 서로 다른 주제 사이에 충분한 여백을 둔다.
- 기존 소단원의 3~5개 독립 이미지·도해 구성을 기준으로 실제 수량을 확인한다. 교정 때문에 장식용 그림을 늘리지 않는다.
- 종합 사례는 각각 3개의 독립 도해를 기본으로 한다. 한 장에 모든 설명을 몰아넣지 않는다.
- 학생 화면에는 버전 번호·내부 식별자·개발 검수 항목을 노출하지 않는다.
- 한 활동에서 결과를 보여주는 시점과 학생에게 예측을 요구하는 시점이 뒤섞이지 않게 한다.

### 2.2 이미 확인한 것과 후속 확인이 필요한 것을 구분한다

| 항목 | 현재 확인 근거 | 후속 조치 |

| 단원 시험 수 문구 | 실제 lessonPreset은 6개, 미사용 기본 preset 문구에는 10개가 남아 있음 | 실제 표시 경로를 확인하고 학생용 수량 설명을 일치시킨다. |
| 그림·문항 간 중복 | 지난 검사에서는 정확히 같은 문제 문장은 없음 | 의미가 같은 반복 문항, 정답 힌트 유출 여부는 사람이 별도 판단한다. |

현재 발견 목록을 전체 검수 결과로 간주하지 않는다. 기존 원고와 그림은 읽고 대조한 범위만 완료로 기록한다.

## 3. 공통 실행 방식

### 3.1 작업 단위

- 기본 편집 묶음: **대단원 1개 = 소단원 2개 = 본문 주제 12개 + 확인 문제 6개 + 시험 문항 12개 + 해당 실습**.
- 각 묶음에서 A를 먼저 끝내고, 정해진 개념·용어를 B와 C에 사용한다.
- 공통 데이터·실습 연결 구조는 대표 예제로 먼저 확정한다.
- 한 묶음의 검토 결과를 기록한 뒤 다음 묶음으로 진행한다. 매번 24개 대단원을 다시 읽지 않는다.
- 공통 모델이 바뀌면 해당 모델을 사용하는 미션·사례만 다시 검증한다.

### 3.2 완료 상태

검수대장의 상태는 `미착수 → 검토 중 → 수정 필요 → 재검증 → 완료`로 관리한다.

수정할 것이 없는 주제도 근거·관찰 결과를 남긴 뒤 완료한다. 미지원 환경이나 근거 부족은 완료 처리하지 않고 남은 조건을 기록한다.

### 3.3 이슈 기록

각 이슈에 다음 항목을 남긴다.

| 항목 | 기록 내용 |
| --- | --- |
| 식별자 | 예: A-CH15-L02-01 |
| 위치 | 원본 파일·lessonId·sectionId·그림 또는 labId·questionId |
| 기존 상태 | 문제 문장 또는 재현할 입력·조작 |
| 학습 영향 | 어떤 오해를 만들거나 어떤 결과를 잘못 판단하게 하는가 |
| 근거 | 공식 문서의 관련 절, 독립 계산, 실제 출력 |
| 수정안 | 바꿀 문장·도해·모델 또는 선택지 |
| 함께 바꿀 곳 | 안내·본문·확인 문제·시험·연결 용어·미션 |
| 확인 결과 | 기대값, 관측값, 근거 파일 또는 화면 |
| 상태 | 미착수/검토 중/수정 필요/재검증/완료 |

우선순위는 정답·수치·보장을 잘못 가르치는 문제, 관찰·조작을 방해하는 문제, 읽기 표현 순서로 정한다.

## 4. A — 본문·그림·실습 대조 검수

### 4.1 소단원 하나의 검수 순서

1. 소단원의 학습 목표 3개와 선수 지식을 확인한다.
2. 6개 주제에서 핵심 주장·정의·수치·조건을 추출한다.
3. 모든 그림의 제목·라벨·화살표·순서·강조와 본문을 대조한다.
4. 실습의 기본 상태, 입력 적용, 중간 상태, 결과, 오류 입력을 재현한다.
5. 본문의 수식·표·예시를 독립 계산하거나 공식 근거와 대조한다.
6. 실습 안내 네 문장이 실제 표시·조작과 맞는지 확인한다.
7. 확인 문제 3개와 핵심 정리가 앞에서 설명한 개념을 정확히 묻는지 확인한다.
8. 관련 시험 6개와 미션의 전제가 바뀌는지 표시한다.
9. 필요한 부분만 교정하고 해당 주제의 이해 흐름을 다시 읽는다.
10. 검수대장에 주제별 결과와 미해결 항목을 남긴다.

### 4.2 공통 검수 질문

| 관점 | 확인할 내용 | 대표 문제 |
| --- | --- | --- |
| 정의 | 용어를 처음 쓰는 지점에서 무엇인지 설명하는가 | 캐시를 정의하지 않고 캐시 히트부터 설명 |
| 비유 | 비유의 각 대상이 실제 무엇에 해당하는가 | 작업자와 CPU·쓰레드를 번갈아 같은 대상으로 취급 |
| 조건 | 평균/최악, 제품/표준, 모형/실제를 구분하는가 | 모든 BST가 O(log n)이라는 단정 |
| 수치 | 단위·초기값·단계 수·반올림 기준이 같은가 | Mb/MB 혼용, p95 표본 기준 불일치 |
| 도해 | 화살표가 관계·시간·데이터 이동 중 무엇을 뜻하는가 | 대기 완료가 바로 실행으로 연결됨 |
| 관찰 | 안내에서 언급한 값이 실제 화면에 존재하는가 | 표시하지 않는 예상 행 수를 비교하라고 지시 |
| 조작 | 입력값과 적용된 조건, 실행 결과를 구별하는가 | 입력만 고쳤는데 이전 결과를 새 결과처럼 표시 |
| 실패 | 오류·미완료·빈 결과·정상 0을 구별하는가 | 표본 없음이 오류율 0%로 보임 |
| 정리 | 핵심 정리와 확인 문제에 새 지식이 갑자기 나오는가 | 본문에 없는 예외를 정답 근거로 사용 |
| 표현 | 자연스러운 문장, 지시 대상, 한글·영문 표기가 일관적인가 | 번역이 섞인 용어, 설명 없는 약어 |

### 4.3 출처와 그림 교정

- 기존 참고 자료를 우선 재사용하되 해당 주장을 실제로 지원하는 절을 확인한다.
- 애매한 제품 동작·표준·보장은 구현 단계에서 공식 문서·원저자 교재·표준 문서를 확인하고 날짜·버전을 기록한다.
- 자동 검사는 링크·ID·파일 누락과 계산 불변조건을 검사한다. 설명의 진실성이나 그림의 교육 효과를 자동 통과로 판정하지 않는다.
- CSS/SVG 도해는 필요한 라벨·연결·순서만 수정한다. 계산 결과를 그림에 고정할 경우 실습의 참조값과 연결한다.
- 생성 이미지 수정이 필요하면 대상 이미지를 먼저 보고, 본문 개념·등장 대상·장면 순서를 정한 뒤 생성·편집한다.
- 생성 이미지에는 정확해야 하는 긴 문장·수식을 맡기지 않고 HTML 설명으로 분리한다.
- 이미지 생성·교체는 실제 불일치가 있는 경우에만 진행한다. 기존 3~5장 구성을 통째로 다시 만들지 않는다.
- 원본·최적화 이미지·프롬프트 기록·대체 텍스트·캡션을 함께 갱신한다.

- [ ] 수치·보장·정답에 영향을 주는 미해결 오류가 없다.
- [ ] 필요한 정정 사항이 시험·미션·관련 용어에도 반영되었다.

## 5. B — 시험 선택지·오답 해설 개선

### 5.1 문항 편집 규칙

- 문항당 한 가지 판단을 묻고 필요한 상황·조건을 문제 안에 제공한다.
- 3개 선택지는 같은 개념 영역·문법·구체성 수준을 유지한다.
- 정답만 유난히 길거나 정교한 설명이 되지 않게 한다.
- 오답은 실제 혼동을 반영한다. 무관한 장치·색상·기능을 넣어 정답을 쉽게 드러내지 않는다.
- 초심자가 이해할 수 있는 상황·수치로 작성한다. 난이도를 높이려고 용어만 어렵게 바꾸지 않는다.
- 1개 정답과 2개 오답이 왜 구분되는지 작성자가 각각 설명할 수 있어야 한다.
- 동일 핵심 개념의 반복은 허용하되 같은 상황·같은 사고 과정·같은 정답을 단어만 바꿔 반복하지 않는다.
- 시험 중 정답·해설을 노출하지 않고 제출 뒤 선택지별 해설을 제공한다.
- 공개 전 난이도 표시는 편집상 분류에 한정한다. 실제 학생 수준 진단에 검증된 수치로 사용하지 않는다.

### 5.2 선택지별 해설 864개

| 종류 | 수량 | 작성 기준 |
| --- | --- | --- |
| 정답 해설 | 288개 | 결정적인 조건과 원리를 설명하고 필요한 경우 짧은 계산을 포함 |
| 오답 해설 | 576개 | 선택한 답의 혼동 → 문제에서의 반례·조건 → 올바른 판단 순서 |
| 미응답 안내 | 화면 공통 | 틀린 생각을 추정하지 않고 정답 근거와 본문 링크 제공 |

오답 해설은 보통 2~3문장으로 작성한다. 글자 수를 채우는 검사를 품질 기준으로 사용하지 않는다.

예시 — 누적 ACK:

> 문제: 연결이 설정된 TCP에서 누적 ACK 101을 받았습니다. 순서 번호가 한 바퀴 돌아가는 경우를 제외하면 무엇을 뜻할까요?
>
> 정답: 100까지의 바이트를 연속으로 받았고 101부터 기다린다.
>
> 오답 A: 101까지 받았으므로 102부터 기다린다.
>
> A 해설: ACK 번호를 마지막으로 받은 번호로 해석했어요. 누적 ACK는 다음에 기대하는 바이트 번호이므로, ACK 101은 100까지 연속으로 받았다는 뜻이에요.
>
> 오답 B: 이 ACK가 확인하는 것은 101번 바이트 하나뿐이다.
>
> B 해설: 누적 확인을 개별 바이트 확인으로 해석했어요. ACK는 번호 하나에만 붙이는 수신 표시가 아니라 그 번호 앞까지 연속 수신한 구간을 나타내요.

### 5.3 데이터 구조 변경안

작성용 데이터는 선택지 ID·내용·해설을 한 객체에 둔다. 화면용 questions 구조는 최대한 유지한다.

```js
{
  id: 'ch15-l02-e02',
  revision: 4,
  lessonId: 'ch15-l02',
  reviewSectionId: 'b02',
  tag: 'application',
  prompt: '...',
  correctChoiceId: 'next-expected',
  choices: [
    { id: 'next-expected', text: '...', feedback: '...' },
    { id: 'last-received', text: '...', feedback: '...',
      misconceptionId: 'ack-is-last-received' },
    { id: 'single-byte-only', text: '...', feedback: '...',
      misconceptionId: 'ack-confirms-one-byte' }
  ]
}
```

- 현재 위치 기반 `chXX-lXX-eXX` 문항 ID는 명시적인 작성 필드로 옮기고 유지한다.
- 선택지 ID는 표시 순서와 독립적으로 고정한다. 정답·해설·학생 답안을 같은 ID로 연결한다.
- 선택지를 섞을 때 객체 전체를 함께 옮기고, 화면용 feedback 배열은 최종 options 순서에서 생성한다.
- 각 문항에 reviewSectionId를 명시해 작성 순서와 본문 위치가 우연히 같다는 가정을 제거한다.
- 미교정 문항은 revision 3, 교정 문항은 4로 구별한다. 이후에도 내용이 바뀐 문항만 revision을 올린다.
- 전환 기간에는 기존 q(...) 문항과 새 객체 문항을 모두 읽는다. 288개 이관 완료 뒤 기존 형식 지원 제거 여부를 결정한다.
- 단원 확인 문제 144개는 A 범위에서 기존 형태를 유지하고, 새 저장 키에서 revision 1로 구분한다.

### 5.4 응시·복습 호환

1. 진행 중·제출 완료 응시는 기존에 저장한 questions 사본으로 복원하고 채점한다.
2. 새 시험만 새 문항을 사용한다. 교정 후 옛 시험 점수를 재계산하지 않는다.
3. 복습 항목의 식별 기준을 `question.id + revision`으로 바꾼다.
4. 옛 복습 항목은 저장된 question.revision을 사용한다. 값이 없으면 기존 문항 형식을 판별하고 판별 불가능한 항목은 원문 보존 상태로 둔다.
5. 같은 문항 ID라도 revision이 다르면 새 선택 ID를 옛 question 사본에 기록하지 않는다.
6. 기존 `#review/<itemId>` 링크는 별칭 조회로 계속 연다. 변환 전 원본과 항목 순서·완료 상태를 보존한다.
7. 정상 변환과 저장 성공을 확인한 뒤 저장 형식을 갱신한다. 실패 시 기존 저장 내용을 덮어쓰지 않는다.
8. 옛 복습을 최신 문항으로 풀어보는 경우에는 별도 시도로 만들고 이전 기록을 변경하지 않는다.

## 6. C — 57개 실습의 비교 미션

### 6.1 학습 흐름

```text
미션 선택 → 시작 조건 확인 → 결과 예측
          → A 실험 → A 결과 기록
          → 한 조건을 바꾼 B 실험 → B 결과 기록
          → 차이 확인 → 내 설명 작성 → 해설과 자기 점검
```

- 각 실습 아래에 접을 수 있는 “비교해 보기” 영역을 추가한다.
- 기본 화면에는 미션 제목·목표·예상 활동 시간만 간결하게 표시한다.
- 미션을 펼치면 기존 guide 네 문장을 다시 나열하지 않고 구체적인 A/B 조건을 보여준다.
- 학생은 “A 조건 불러오기”로 조건만 적용하고, 기존 실습 버튼으로 직접 실행한다.
- A 결과를 기록한 뒤 B 조건을 적용해도 A 결과는 유지된다.
- 자동 입력은 학습 설정을 준비하는 데만 사용한다. 예측·실험·결과 확인을 몰래 한 번에 완료하지 않는다.
- “해설 먼저 보기”도 허용하되 실험을 수행하거나 이해를 확인한 것으로 처리하지 않는다.

### 6.2 미션 하나의 필수 내용

| 항목 | 기준 |
| --- | --- |
| 목표 | “어떤 차이를 설명할 수 있는가” 한 문장 |
| 선수 지식 | 해당 주제 또는 먼저 읽을 소단원 링크 |
| 고정 조건 | 데이터·크기·실행 순서·모형 가정 |
| 바꿀 조건 | 비교축 한 개. 추가 실험은 별도 단계로 분리 |
| 예측 | 실행 전에 값·방향·상태를 골라 보거나 적기 |
| A/B 조작 | 현재 실습의 실제 입력 이름·버튼과 일치 |
| 기록할 결과 | 화면과 모델에서 실제 확인 가능한 1~3개 지표 |
| 기대 결과 | 독립 계산 또는 참조 실행값, 필요한 허용 오차 |
| 설명 과제 | 결과 차이가 생긴 원인을 학생 언어로 설명 |
| 자기 점검 | 설명에 필요한 2~3개 핵심 요소 |
| 적용 한계 | 교육용 계산을 실제 성능·보장으로 일반화하지 않기 |
| 복습 링크 | 해당 lessonId·sectionId로 이동 |

전체 57개 설계는 [비교 미션 설계목록](비교미션_설계목록.md)에서 관리한다.

### 6.3 실습 연결 구조

제안 파일:

- `content/lab-missions.js`: 학습 문장, A/B 설정, 관찰 지표, 복습 위치.
- `src/learning/mission-model.js`: 단계 이동, A/B 기록, 수치·상태 판정.
- `src/learning/lab-adapters.js`: labId별 설정·결과 추출·완료 조건.
- `src/learning/mission-view.js`: 미션 화면과 기존 실습 연결.
- `src/learning/storage.js`: 미션·사례 초안 저장.
- 기존 `src/app.js`: 미션을 연결할 작은 수명주기 훅.
- 기존 `scripts/build.cjs`: 모듈을 명시적 의존 순서로 포함.

어댑터의 계약은 `prepare(scenario) → observe() → canRecord() → capture()`로 통일하되 내부에서는 각 실습의 기존 validate·initial·step·action을 호출한다.

- 단계형 15개: 현재 완료 상태·진행 단계·입력 적용 여부를 사용한다.
- 버튼형 42개: 검색 수행, 복구 실행, 질의 성공 등 미션별 완료 조건을 명시한다.
- `state.done`의 존재나 “끝까지”라는 버튼 이름만으로 완료를 판단하지 않는다.
- SQL·Web Crypto·이벤트 루프는 실제 비동기 완료 뒤에만 결과를 기록한다.
- SQL 비교는 매 시나리오의 초기 DB 조건을 확인해 이전 CREATE INDEX 등이 다음 결과에 남지 않게 한다.
- 결과 추출은 숫자·상태·결과 행 같은 구조화 데이터를 사용한다. 설명 문장이나 로그를 파싱해서 정답을 만들지 않는다.
- 같은 실습을 종합 사례에서도 재사용할 수 있도록 화면 인스턴스별 상태를 분리한다.
- 전체 app.js를 재작성하지 않는다. 공유가 필요한 mount/dispose/observe 부분만 추출한다.
- 입력 수정·초기화·오류·이전 상태 복원 시 A/B 결과의 유효성을 다시 계산한다.
- A 또는 B 조건이 바뀌면 해당 조건의 결과와 설명 확인 상태를 만료시킨다. 다른 조건의 결과는 보존한다.
- 비동기 실행 중 이탈·초기화 시 늦게 도착한 결과가 새 미션에 반영되지 않게 한다.

### 6.4 기록과 판정

```js
{
  missionId: 'bst-traversal-compare-01',
  revision: 1,
  phase: 'compare',
  prediction: '...',
  runs: {
    A: { configKey: 'balanced-five', metrics: { comparisons: 3 } },
    B: { configKey: 'ascending-five', metrics: { comparisons: 5 } }
  },
  explanation: '...',
  selfChecks: { sameKeys: false, treeShape: false, pathLength: false },
  updatedAt: 0
}
```

- 상태는 `예측 전 / 실험 중 / 결과 기록 완료 / 설명 정리 완료`로 표시한다.
- 수치·경로·상태는 모델을 기준으로 확인한다. 단순 버튼 클릭 횟수로 완료시키지 않는다.
- 자유 서술은 키워드 포함 여부로 자동 채점하지 않는다. 모범 설명과 자기 점검을 제공한다.
- “설명 정리 완료”는 학생이 작성·자기 점검을 마친 상태이며, 이해도가 객관적으로 검증됐다는 뜻으로 표시하지 않는다.
- 기록은 프로젝트 전용 localStorage 키에 저장한다. 저장 차단 시 현재 화면에서 계속 사용하고 재방문 시 보존되지 않음을 알린다.
- 저장 내용은 필요한 설정·측정값·초안만 포함한다. 전체 DOM·실습 로그·원시 DB를 저장하지 않는다.
- NaN·Infinity·미측정 값을 JSON에서 null과 혼동하지 않게 구조화한다. 예: `{kind:'unreachable'}`, `{kind:'measured',value:0}`.
- 스냅샷에는 함수·Worker·AbortSignal을 넣지 않는다. 저장된 데이터는 버전·유형·크기를 검증하고 텍스트로 안전하게 렌더링한다.
- 변경이 없는 입력을 매 프레임 저장하지 않는다. 결과 기록·단계 전환·입력 디바운스 시 저장한다.

| `#case/<id>/hypothesize` | 가설 선택과 이유 작성 |
| `#case/<id>/experiment` | 기존 실습을 사용하는 비교 실험 |
| `#case/<id>/compare` | 가설과 관측 결과 대조 |
| `#case/<id>/explain` | 최종 설명·자기 점검·관련 단원 |

해시 직접 진입 시 이전 답변이 없어도 오류 대신 필요한 시작 단계와 자료를 안내한다. 단원으로 이동해 참고한 뒤 같은 사례 단계로 돌아오는 링크를 제공한다.

### 7.2 공통 사례 구조

1. **증상**: 사용자가 겪는 문제를 2~3문장으로 제시한다.
2. **관측 자료**: 학습용 요청 기록·값·시간표를 먼저 보여준다.
3. **가설**: 타당한 후보 3개에서 근거를 골라 보게 한다.
4. **실험**: 가설을 구분할 수 있는 비교 미션을 실행한다.
5. **판단**: 처음 가설을 유지하거나 수정하고 이유를 적는다.
6. **개선안**: 어떤 조건을 바꿀지, 어떤 지표로 효과를 확인할지 고른다.
7. **설명**: 관측 → 원인 후보 → 실험 결과 → 개선안 → 한계를 정리한다.

가설 선택을 단순 정오답 퀴즈로 끝내지 않는다. “그럴 수 있지만 이 자료로는 확인하지 못했다”와 “관측과 충돌한다”를 구별한다. 잘못된 가설을 선택해도 실험 후 수정할 수 있다.

### 7.3 사례 D-01 — 웹사이트 일부 요청이 유독 느려요

| 항목 | 설계 |
| --- | --- |
| 연결 단원 | CH05-L02 시간·네트워크, CH13-L02 실행 계획, CH24-L02 관측 |
| 선수 개념 | 지연·처리량, 인덱스, 평균·백분위수 |
| 시작 자료 | 요청 10개 중 9개는 10ms, 1개는 1000ms인 학습용 표본 |
| 추가 자료 | 느린 요청 하나의 순차 구간: 네트워크 60ms + 서버 계산 60ms + DB 880ms = 1000ms |
| 가설 후보 | 모든 요청의 네트워크가 느림 / 특정 DB 경로가 느림 / 평균만으로 이상이 없다고 판단 |
| 실습 재사용 | observability-recovery, query-plan |
| 예측 | 평균과 p95가 각각 무엇을 보여줄지 예상 |
| 첫 관측 | 평균 109ms, 최근접 순위법 p95 1000ms |
| 비교 실험 | 동일 데이터·동일 WHERE 조건에서 인덱스 유무에 따른 접근 계획 비교 |
| 판단 | 제공한 구간 기록은 해당 요청의 DB 구간을 조사할 근거이며, 전체 장애 원인 확정은 아님 |
| 개선안 | 인덱스·조건·실제 행 수를 점검하고 수정 전후 같은 조건으로 지연을 다시 측정 |
| 설명 기준 | 평균의 한계, 특정 경로의 근거, 계획과 실제 시간의 차이 |

필수 주의:

- 구간 시간표는 이 사례를 위해 만든 **학습용 관측 자료**라고 표시한다.
- 실제 SQLite의 작은 예제에서 SCAN이 SEARCH로 바뀐 것을 “실제 사이트가 몇 배 빨라졌다”로 표현하지 않는다.
- SQLite EQP가 실제 제공하는 detail만 사용한다. 실행 시간·페이지 I/O·예상 행 수를 만들어내지 않는다.
- 원래 질의와 인덱스 질의의 결과 동등성은 실제 SELECT 결과를 별도로 확인한다. ORDER BY가 없다면 행 순서가 아니라 행의 내용·개수를 비교한다.

독립 도해 3개: 요청별 지연 분포 / 한 요청의 처리 구간 / 접근 계획과 측정 검증의 관계.

### 7.4 사례 D-02 — 저장했다고 생각한 데이터가 사라졌어요

| 항목 | 설계 |

| 구성 | 같은 “데이터가 안 보임”을 세 개의 독립 실험으로 분해 |

필수 주의:

- 네 실습을 실제 하나의 시스템에서 동기화된 데이터처럼 표시하지 않는다. 각 실험이 같은 증상의 다른 원인 후보를 설명한다는 관계를 밝힌다.
- 쓰기 실패 응답이나 응답 손실만으로 데이터가 반드시 저장되지 않았다고 단정하지 않는다.
- 마지막 복구 지점과 장애 시각의 간격은 손실 가능한 시간 범위다. 실제 삭제된 레코드 수를 제공한 것처럼 설명하지 않는다.
- 복구 목표 숫자를 느슨하게 바꾸어 충족 표시가 나와도 실제 복구 성능이 개선된 것으로 표현하지 않는다.

독립 도해 3개: 작업 메모리·확정 저장·복제본 / WAL 기록과 장애 시점 / RPO·RTO 시간선.

3. C의 기본 미션과 실험 근거.
4. 영향받은 데이터·계산·호환 검사.
5. 해당 기능의 실제 브라우저 재현.
6. 검수대장과 변경 이력 기록.

새 구조는 먼저 대표 묶음으로 검증하고 이후 반복 집필한다. 전체 문항·미션을 한 번에 바꾼 뒤 문제를 찾는 진행은 피한다.

### 9.3 작업량·소통 기준

- A: 48개 소단원 × 주제 6개, 확인 문제 144개, 기존 그림 전체.
- B: 288개 문항의 편집 판단 + 선택지별 해설 864개.
- C: 공통 연결 구조 + 57개 기본 미션 + 미션별 참조 조건.
- D: 3개 사례 × 7단계 내외 + 도해 9개.
- 전체 완료 기간은 P1~P3에서 대표 묶음을 끝낸 실제 작업량으로 다시 산정한다. 검토 전 날짜를 확약하지 않는다.
- 진행 보고는 완료한 묶음·발견한 핵심 문제·남은 범위만 간단히 전달한다.
- 부분 배포 시 학생에게 보이는 것은 완성된 문항·미션·사례로 한정한다. 빈 메뉴나 미완성 사례 링크를 노출하지 않는다.

## 10. 검증 계획

### 10.1 데이터와 교육 내용

| 대상 | 자동 확인 | 직접 확인 |

| C | 57개 대응·A/B 독립성·설정 유효성·판정·기대값 | 실제 버튼과 지시 일치·관측 지점·설명 기준 |

문장 길이·키워드 수·스크린샷 개수만으로 교육 품질을 통과시키지 않는다.

### 10.2 필요한 회귀 사례

- 시험 선택지 6개 순열에서 정답·오답 해설·저장된 답안 연결 유지.
- revision 3 응시를 저장한 뒤 revision 4 콘텐츠를 불러와도 옛 시험 복원·점수 유지.
- 동일 문항 ID의 새 revision 오답이 옛 복습 항목의 선택지를 오염시키지 않음.
- 본문 순서가 바뀌어도 명시한 reviewSectionId로 복습 가능.
- 미션 A 기록 후 B 입력 변경·초기화·오류가 A를 덮어쓰지 않음.
- 입력만 고친 상태에서 이전 실행 결과를 새 조건의 결과로 기록할 수 없음.
- 도달 불가·빈 결과·0과 미실행을 구별.
- 비동기 실행 중 이탈한 결과가 다음 화면에 표시되지 않음.
- 완료 상태가 없는 버튼형 실습에서도 실제 검색·질의·복구 완료를 판정.
- SQL A/B 실행이 이전 인덱스·데이터를 공유해 비교 조건을 오염시키지 않음.
- 사례 직접 주소 진입·이전 단계·본문 왕복에서 초안과 실험 근거 유지.
- 저장 실패·손상 데이터·옛 버전 기록을 정상 완료로 오인하지 않음.

### 10.3 실행·배포 확인

- 개발 중에는 수정한 영역의 관련 검사를 먼저 실행한다.
- 배포할 묶음이 완성되면 전체 `npm test`, `npm run build`, `git diff --check`를 실행한다.
- 웹판과 단일 파일판에 새 데이터·스크립트·도해가 포함되는지 확인한다.
- 단일 파일판 직접 실행 여부는 실제 확인한 실행 환경만 기록한다. HTTP 미리보기를 오프라인·file 실행 검증으로 대신 기록하지 않는다.
- 동작 확인은 이번에 추가·수정한 미션·시험·사례 흐름을 대상으로 한다.
- GitHub Pages의 해당 커밋 배포 성공 후 공개 주소에서 완료된 대표 흐름을 확인한다.
- 배포된 정적 JS에 답안·해설이 포함되는 기존 구조를 유지하며 공식 성적 인증 기능으로 소개하지 않는다.
